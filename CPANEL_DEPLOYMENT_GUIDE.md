# cPanel staging and deployment guide

**Do not deploy this branch to production yet.** Critical implementation and verification remain in REMAINING_ACTIONS.md. The steps below describe a plan to rehearse in a separate staging account, not a verified production procedure.

1. Confirm hosting supports a supported WordPress version, PHP 8.1 or newer (the code uses `str_starts_with`), MySQL/MariaDB, HTTPS, WordPress-required PHP extensions and sufficient upload and database limits. Exact supported version combinations have not been tested. Confirm cost before provisioning.
2. In cPanel, use the host's WordPress installer/WP Toolkit if available, or follow the [cPanel WordPress installation guide](https://docs.cpanel.net/knowledge-base/third-party/how-to-install-wordpress-with-cpanel/104/). Create a dedicated staging database and least-privilege database user using cPanel's database tools. Store credentials securely in the staging `wp-config.php`; never put them in Git or chat.
3. Restrict staging access and indexing. Back up existing files, database, configuration and any private files before touching an existing installation; practice restoring them to a separate environment.
4. Install the compatible updated IGP theme first, then the independent IGP Core plugin, through WordPress Appearance → Themes and Plugins → Add New. Confirm backups and compatibility before upgrading an existing installation. The theme keeps a fallback until the plugin is activated; do not install this preliminary code on a production site.
5. Under Settings → Permalinks choose and save an appropriate permalink structure. On an intentionally empty staging catalogue, use Tools → IGP catalogue import once. Existing catalogue records are not overwritten; the importer is not safely resumable after interruption. Test and verify data before any real migration.
6. Configure Settings → IGP Settings, including the approved notification recipient. Install and configure a trusted authenticated SMTP provider/plugin separately without committing credentials. Test delivery and failure handling; WordPress reporting a successful send is not delivery confirmation.
7. If the host permits a directory outside every publicly served document root, create a directory owned by the application user with restrictive access and define `IGP_PRIVATE_STORAGE_DIR` in staging `wp-config.php` using the host-confirmed absolute path. The code rejects paths inside the WordPress root or reported document root; verify actual server aliases, symlinks and public access with the host. Backup this directory with the database. If unset, attachment bytes are stored in the WordPress database; protect its backups. Test PHP `upload_max_filesize`, `post_max_size`, memory, execution time and database packet limits. Storage and access remain unverified on cPanel.
8. Set up HTTPS/TLS, strong individual accounts, MFA where possible, updates, file permissions and rate-limiting. Consult [WordPress hardening guidance](https://developer.wordpress.org/advanced-administration/security/hardening/) and your host. Do not expose private uploads or database backups.
9. Rehearse testing: customer form and duplicate retries, product/category CRUD, all 80 products, attachment access for authorized and unauthorized users, role restrictions, email failures, accessibility, mobile, caching, database outages, backup and restore.
10. Before any approved domain cutover, inventory existing DNS records including Websouls MX, SPF, DKIM and DMARC. Coordinate changes with the email administrator; preserve existing mail records and verify email delivery. Configure the canonical domain and redirects only after TLS and routing are verified.
11. Record the current application version and complete tested backups; plan how to restore database, public media and private files together. A code rollback alone does not revert customer data. Rehearse staging-to-production migration and rollback, monitor errors and enquiries, and obtain explicit approval before production changes.
